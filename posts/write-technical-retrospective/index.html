技术复盘需要让读者知道发生了什么、为什么这样判断，以及下一次如何确认结果。把事实、判断、行动和验证分开写，文章就能从过程记录变成可复用的方法。

先写可核对的事实

事实应当能回到仓库、命令或构建产物。以 blok-ds 为例，当前仓库可以直接确认这些内容：

  • 文章文件位于 src/content/posts/，由 Astro Content Collections 读取。
  • astro.config.mjs 从 BASE_PATH 生成项目站点的 base。
  • .github/workflows/main.yml 使用 SITE 和 BASE_PATH 执行 pnpm build。
  • src/lib/site.ts 集中生成首页、文章页和 RSS 使用的站内路径。

这些句子描述的是已有文件和配置。它们可以作为复盘的证据，也能帮助读者在自己的仓库中找到对应位置。

再记录判断和行动

事实说明现状，判断说明影响，行动说明准备改变什么。下面是一段明确标注为示例的记录：

示例判断：项目站点的链接如果绕过 src/lib/site.ts，部署到 /blok-ds/ 后可能缺少项目路径。

示例行动：让新增的站内链接使用 url() 或 postPath()，并用带 BASE_PATH=/blok-ds 的构建检查产物。

这种写法把可验证的依据和作者的推断分开。读者可以先复现事实，再判断行动是否适合自己的项目。

让验证结果能重做

本仓库的静态站点可以用一组短命令验证构建是否仍然可用：

bash
set -eu

pnpm install --frozen-lockfile
SITE=https://shortlight5980.github.io BASE_PATH=/blok-ds pnpm build

test -f dist/index.html
test -f dist/rss.xml
grep -q '/blok-ds/' dist/index.html

复盘中记录完整命令和预期结果，其他人就能在相同输入下重做检查。若结果改变，也能定位变化发生在内容、构建参数还是页面路径。

用结论收束文章

一篇可读的技术复盘，结论应回答两个问题：这次观察带来了什么可执行的规则，下一次用什么检查确认它仍然成立。对项目子路径部署来说，规则是统一生成站内路径，检查是用 /blok-ds/ 构建并核对产物中的链接。这样的结论短小，却足以指导下一次改动。

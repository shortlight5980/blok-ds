# 协作约定

本文件说明仓库里的角色、职责边界与决策方式。目标是让人类与多个 agent 并行工作时，改动可预测、可回溯。

## 角色

| 角色 | 由谁承担 | 主要职责 |
| --- | --- | --- |
| 维护者 | 仓库所有者（人类） | 产品方向、视觉风格、仓库设置、合并、发布 |
| 分派者 | 编排 agent | 接收需求、拆分任务、分派与汇总 |
| Worker | 执行 agent | 调研、实现、测试、自审、提交 PR |
| 评审者 | 人类或指定 agent | 审查改动与证据，提出可执行意见 |

## 职责边界

- Worker 只做任务简报内的改动；发现范围外的必要改动时，先说明原因再扩展，或者交还分派者。
- Worker 不修改其他任务的分支，不关闭 Issue，不自行合并 PR，不擅自修改仓库设置（Pages、可见性、域名、密钥）。
- 维护者负责需要产品判断的决定：博客名称、视觉方向、域名、评论/统计等外部服务。
- 结构性决定（技术栈、目录布局、部署方式）需要 ADR，并由维护者确认。

## 决策权

| 事项 | 决定者 |
| --- | --- |
| 视觉风格与页面结构 | 维护者 |
| 功能范围与优先级 | 维护者 |
| 具体实现方式 | Worker（在既有设计与约定内） |
| 技术栈 / 架构变更 | ADR + 维护者确认 |
| 合并与发布 | 维护者 |

没有明确指示时，按“现有 Issue 要求 → 设计文档 → 现有代码风格”的顺序取舍；仍无法判断时升级给维护者，不自行猜测产品方向。

## 完成定义

一项任务可交付，需同时满足：

- 验收标准满足，改动聚焦。
- `pnpm build` 通过，相关检查已执行并记录。
- 文档与设计同步更新。
- UI 改动有前后对比证据（基线版本、视口、主题明确）。
- PR 自审完成，风险与限制写清楚。

## 冲突与升级

- 需求互相矛盾时，列出冲突点与影响，交给维护者决定。
- 实现反复失败或需要破坏既有约定时，保留可用的部分，标明未完成项，升级而不是绕过保护。
- 不把需要人类判断的产品问题伪装成技术选择。

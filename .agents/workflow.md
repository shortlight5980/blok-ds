# 开发流程

从 Issue 到上线的标准路径。小改动可以合并步骤，但不能跳过验证与评审。

## 1. 任务

- Issue 是需求的来源；范围不清时先问，不靠猜测扩大范围。
- 开始前读 [`AGENTS.md`](../AGENTS.md)、本目录文档，以及 [`templates/task-brief.md`](templates/task-brief.md)。
- 一个任务保持一个目标；顺手改动拆成单独任务。

## 2. 分支

- agent：`agent/<短描述>`，例如 `agent/init-blog-site`。
- 人类：`feat/<短描述>`、`fix/<短描述>`、`docs/<短描述>`。
- 从最新 `main` 拉出；不直接向 `main` 提交。

## 3. 提交

- 一条提交做一件事，信息说明“做了什么、为什么”。
- 推荐格式：`<type>: <摘要>`，type 取 `feat` / `fix` / `docs` / `style` / `refactor` / `chore` / `test`。
- 摘要用祈使句、短句；正文需要时说明背景与验证方式。
- 不提交生成物、依赖目录、本地环境文件。

## 4. PR

- 标题与提交风格一致；正文包含：
  - 变更内容与原因；
  - 验证方式（实际运行的命令与结果）；
  - 视觉证据（UI 改动必须有前后对比，注明基线版本、视口、主题）；
  - 风险、限制与后续工作。
- 关联对应 Issue；一个 PR 只解决一个任务。
- 创建后先自审 diff，再请求评审。

## 5. 构建检查

- 提交 PR 前本地执行 `pnpm install --frozen-lockfile && pnpm build`，并在 PR 记录结果。
- 当前未配置 CI 工作流；需要自动化时，按设计文档 §11 添加 GitHub Actions 工作流。
- 失败先查日志修复；不通过跳过检查、禁用工作流或降低标准来“变绿”。
- 新增依赖时提交 `pnpm-lock.yaml`。

## 6. 评审

- 评审意见逐条处理：修复、说明不采纳的理由，或交还讨论。
- 修复后重新验证并回复结论；已解决的讨论串关闭。
- 人类评审意见优先于自动评审建议；自动评审只作为参考，不构成合并授权。

## 7. 合并与发布

- 合并由维护者执行；agent 不自行合并，也不开启 auto-merge。
- 合并到 `main` 后，构建产物发布到 `gh-pages` 分支（见 README）；启用 GitHub Actions 后可由工作流自动完成。
- 发布失败时先回滚或 revert 导致失败的提交，再排查；不在失败状态下继续叠加改动。
- 关闭 Issue 由维护者在确认完成后操作。

## 8. 文档

- 行为、结构或约定变化时，同步更新 `.agents/` 下的文档。
- 结构性变更新增 ADR；不要只把决定留在 PR 讨论里。
